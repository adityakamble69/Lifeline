# Lifeline Blood Donor Network — Database Design

**Database:** Supabase PostgreSQL  
**Database project:** `lifeline` (project name can vary by environment)

## 1. Database Principles

- Use PostgreSQL with Supabase-managed storage and Row Level Security (RLS).
- Use foreign keys for relational integrity and Supabase RLS policies for access control.
- Use UTC timestamps in storage; convert for display.
- Prefer PostgreSQL UUID primary keys generated by `gen_random_uuid()` for application entities.
- Use `DECIMAL` only for numeric values that require exact precision.
- Do not duplicate donor/request/camp identity data unnecessarily.
- Add indexes based on actual query patterns.
- Never store plaintext passwords.

## 3. Relationships

```text
users
 ├── 1:1 donor_profiles
 ├── 1:N blood_requests
 ├── 1:N donations (through donor_profiles)
 ├── N:M organizations (organization_members)
 ├── N:M conversations (conversation_members)
 └── 1:N notifications

organizations
 ├── 1:N camps
 └── N:M users

camps
 ├── 1:N camp_registrations
 ├── N:M volunteers
 ├── 1:N donations
 └── 1:N camp_feedback

donor_profiles
 ├── 1:N donor_approvals
 └── 1:N donations

blood_inventory
 └── 1:N inventory_transactions
```

## 4. Important Indexes

Recommended initial indexes:

```text
users(email)

donor_profiles(blood_group, city, availability_status)
donor_profiles(user_id)

blood_requests(blood_group, city, status, urgency)
blood_requests(created_at)

camps(status, start_at, city)
camp_registrations(camp_id, status)
camp_registrations(user_id)

donations(donor_id, donation_date)
blood_inventory(blood_group, location_id, status)
inventory_transactions(inventory_id, created_at)

notifications(user_id, is_read, created_at)
messages(conversation_id, sent_at)

audit_logs(organization_id, entity_type, entity_id)
```

## 5. Constraints

- Email must be unique.
- Camp registration must be unique per user/camp.
- Organization membership must be unique per user/organization.
- Units required/available must be positive where applicable.
- Ratings are restricted to the documented range.
- Status values should use controlled enums or validated application constants.
- Foreign keys use appropriate delete behavior; avoid cascading deletion of important audit/history records.

## 6. Important Queries

### Find active donors

Filter:

```text
blood_group = requested group
city = requested city
availability_status = available
donor approval = approved
```

### Upcoming camps

```text
status = published
start_at >= current time
ORDER BY start_at ASC
```

### Low inventory

```text
units_available <= configured low-stock threshold
```

### Pending donor approvals

```text
donor_approvals.status = pending
ORDER BY created_at ASC
```

## 7. Seed Data

Development seed data should include:

- 1 organization.
- 1 admin/organizer.
- Sample donor accounts across all major blood groups.
- Sample blood requests with different statuses.
- Sample camps and registrations.
- Sample volunteers.
- Sample inventory locations and stock.
- Sample notifications/messages.
- Sample audit logs.

All seed users must use clearly non-production credentials and fake data.

## 8. Security

- Authentication credentials are managed by Clerk; application tables must not store Clerk passwords or password hashes.
- No secret values in seed files.
- Parameterized SQL.
- Least-privilege database account in deployment.
- Supabase URL and server-side service-role credentials are environment variables; never expose the service-role key to the browser.
- Restrict document/file access.
- Audit high-impact admin actions.
- Avoid storing unnecessary sensitive personal information.
